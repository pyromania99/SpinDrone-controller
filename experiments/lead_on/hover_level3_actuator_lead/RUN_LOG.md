# L3 hover — the actuator lead, and what it takes to make it fly

**Flown 2026-09-20.** 38 runs, level 3 (PX4's own estimator, `MC_CTRL_GT=0`), hover at
r ≈ 29.5 rad/s, 60 s hold. Findings live in
[`../../../notes/ACTUATOR_LEAD.md`](../../../notes/ACTUATOR_LEAD.md) §3b and §3c; this file
records **how** they were produced and **where** the raw data is.

## The command

Every run is a variation on one invocation:

```bash
python3 examples/flight/fly.py --level 3 --controller eigen \
  --motor-moment 6e-7 --rotor-tau <TAU> --headless --hold 60 \
  --gains MC_CTRL_ALG=3 MC_CTRL_GT=0 MC_SEAT_MODE=<0|2> MC_POLE_EN=0 IMU_DGYRO_CUTOFF=60 \
          MC_LEAD_EN=<0|1> MC_LEAD_TC=<TC> MC_LEAD_WN=250 MC_LEAD_DMAX=<DMAX>
```

Scored on a 25 s window opening 10 s after the vehicle first reaches 5.5 m, against
`vehicle_*_groundtruth`. "FLEW" means it held the full 60 s.

## ⚠ Reproducing these requires setting `MC_LEAD_DMAX` explicitly

**Every run here booted firmware whose `MC_LEAD_DMAX` default was still 200.** The default
was lowered to **25** in `lead_params.c` *after* these flew, on the strength of what they
show, and SITL was not rebuilt in between. So in the table below:

- a `DMAX` of **200** means the parameter was **never set** and the run took the old default;
- any other value was set explicitly on the command line.

Rebuild the firmware and the unset runs stop reproducing. Set `MC_LEAD_DMAX=200` explicitly
to recover them. The parameter values in the table are read back from each ulog's
`changed_parameters`, not from the scripts, so they are what the vehicle actually flew.

## What is in `logs/`

One folder per run, named by its `px4_runs/` directory: the `.ulg`, the console
(`console.txt`), and `run_config.json`. `manifest.json` is the machine-readable form of the
table below, generated by the same extractor.

## Reading the groups

**Q is the result.** Neither tool alone flies at `rotor_tau = 0.030`; the pair does, 5/5.
Lead alone (14.5–15.1 s) dies *earlier* than seat alone (15.8–16.5 s), and both beat the
11.3 s with neither. The interaction is superadditive — an additive model of the two
improvements predicts ~20 s, not indefinite flight.

**X is the single-variable pair** behind the whole result. Same `rotor_tau`, same `TC`, same
seat, same `WN`: `DMAX = 200` crashes at 22.1 s, `DMAX = 25` flies. The first flying run
changed `DMAX` *and* `TC` together and the effect was initially credited to `TC`; group **T**
settles it by holding `DMAX = 25` and sweeping `TC` over 8/15/20/30 ms, all of which fly.
`X_dmax200_wn400` never took off and carries no information.

**M is the hardware-relevant group.** True pole 0.030, believed pole swept over the
12.5–40 ms spread `ev_delay.ulg` gave, with `DMAX` scaled by
`0.4·(0.50·MC_EIG_TRQ_MAX)/TC` so `TC·DMAX` stays at 0.769 N·m and the feed-forward
authority does not move with `TC`. Under-inversion is free; `TC = 40` (the top of the
measured spread) is a 1-in-3 coin flip; `TC = 50` fails 2/2.

**B** extends the boundary with `TC` matched to the pole — 0.040 and 0.050 both fly, where
seat-alone (group **S**) crashes at 13.2 s and 13.8 s. These are matched-model cells and
bound the best case only.

## Void runs — kept, not deleted

| run | why |
|---|---|
| `M_tc040_b_VOID` | never took off: `Preflight Fail: heading estimate not stable`. A launch-time EKF failure unrelated to the compensator. Re-flown as `M_tc040_b2`. |
| `X_dmax200_wn400` | never took off, same class. |

Both are left in `logs/` and in the manifest with their outcome recorded as `no-takeoff`, so
the run count reconciles and neither can be mistaken for a data point.

## What these runs do NOT establish

1. **`TC` mis-set with `DMAX` left at its default.** Group M scaled the two together by the
   sizing rule. An operator who changes one and not the other is untested.
2. **Anything but hover.** No trajectory profile was flown with the lead on.
3. **A mechanism for the failures.** Three separate things do not close on the current model:
   the departure ramp in group Q is not a pure uncancelled-phase threshold; 20 ms and 40 ms
   in group M are near-mirror phase errors (+12.5° / −12.1°) with opposite outcomes; and the
   group M failures arrive abruptly after 30+ s of flight that is indistinguishable from a
   matched `TC`.
4. **Any warning signature.** An earlier reading of group M claimed metrics rise ~3× before
   departure. That came from window-averaging a run whose scoring window had already clipped
   the start of the departure — it measured the crash, not a precursor. The four surviving
   40 ms runs hold 0.16–0.18° tilt throughout, identical to matched. **Retracted.**

## Tooling

Scoring and manifest extraction were done with throwaway scripts, not `../../tools/`. The
manifest extractor reads `MC_*` from each ulog's `changed_parameters` (gains are applied
post-boot, so they are absent from `initial_parameters`) and falls back to the firmware
default in force at the time — which for `MC_LEAD_DMAX` is 200, not today's 25.
